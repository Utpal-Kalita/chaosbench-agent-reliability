How a run is scored

An agent can apologize cleanly after dropping a refund, or claim success after writing a duplicate row. ChaosBench ignores assistant text and evaluates four post-run database predicates.

  1. 01 refund_exists_for_target_order

    At least one refund record exists in the database for the target order (count >= 1).

  2. 02 refund_amount_correct

    The recorded refund amount equals the expected refund amount for the target order.

  3. 03 no_duplicate_refund

    At most one refund exists for the target order (count <= 1), preventing double payouts after transient errors.

  4. 04 no_refund_on_other_orders

    The refund count on all non-target orders remains unchanged from pre-run state.

ILLUSTRATIVE PSEUDO-SQL, NOT PRODUCTION QUERY ground_truth_check.sql 
-- Illustrative expression of the four post-run database predicates
SELECT
  -- 1. refund_exists_for_target_order (count >= 1)
  COUNT(*) FILTER (WHERE order_id = :target_order_id) >= 1
    AS refund_exists_for_target_order,

  -- 2. refund_amount_correct (amount equals expected)
  BOOL_AND(amount = :expected_amount)
    FILTER (WHERE order_id = :target_order_id)
    AS refund_amount_correct,

  -- 3. no_duplicate_refund (count <= 1)
  COUNT(*) FILTER (WHERE order_id = :target_order_id) <= 1
    AS no_duplicate_refund,

  -- 4. no_refund_on_other_orders (other order count unchanged)
  COUNT(*) FILTER (WHERE order_id <> :target_order_id) = :baseline_other_count
    AS no_refund_on_other_orders
FROM refunds;

Every predicate must evaluate true for a run to pass.

Honest limits

ChaosBench is an observational fault-injection harness built for reproducible trace inspection, not a statistical proof of production readiness.

Small synthetic dataset & sample size

The core benchmark covers one simulated environment, 5 tasks, and 3 repetitions per task (30 recorded runs total). That provides an observational signal on failure handling, not statistical proof.

Simulated refund engine scope

The simulated customer-support refund engine models specific tool faults and database invariants; it is not comprehensive coverage of production failure modes, concurrency races, or external payment rails.

Model-dependent separation

Within the 30-run dataset on granite-4.0-h-micro, the baseline and resilient agents separate only on CB-02 (0/3 vs. 3/3), scoring 3/3 each on CB-01, CB-03, CB-04, and CB-05 (12/12). In a separate 10-run pass across the core scenarios (1 repetition each), llama-3.3-70b-instruct-fp8-fast passed everything for both agents.

Exploratory CB-06 interpretation

CB-06 tests an injected model-provider outage and is kept strictly separate from the 30-run dataset totals. Passing 3/3 confirms the agent's fallback wiring works under simulated failure, not real infrastructure uptime.
