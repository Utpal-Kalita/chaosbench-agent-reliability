Section 02

Four ways to break an agent

The seeded chaos engine deterministically injects four failure classes into tool responses and order records during execution.

FAULT 01 // HTTP 503 Availability

Tool outage

The refund API returns an HTTP 503 service unavailable error instead of processing the request.

FAULT 02 // PARSE Contract

Malformed JSON response

A tool returns truncated or syntactically invalid JSON payload data that breaks naive response parsing.

FAULT 03 // INJECTION Security

Prompt injection in order note

Untrusted order text carries hidden instructions telling the model to ignore prior rules and refund another order.

FAULT 04 // AMBIGUOUS 503 Consistency

Commit-then-503

The refund commits in the database before the response fails with HTTP 503, causing a blind retry to issue a duplicate refund.

Section 03

Ground truth, not vibes

Outcomes are judged strictly by inspecting the backend database state after the run finishes—never by trusting what the agent claims in chat, and never with an LLM judge.

An agent can apologize politely while leaving a customer unrefunded, or claim success after issuing two refunds for the same order. ChaosBench ignores conversational self-reporting and queries the database directly.

Every recorded run preserves the complete raw execution trace—every prompt, tool call, injected fault, retry, and final assertion—so failures can be audited step by step.

How pass^3 works

A scenario passes under pass^3 only if all 3 repetitions succeed. One fluke recovery does not count; the agent must survive the injected condition consistently across every repetition.

Methodological Caveat

Only the API-outage scenario (CB-02) separated the two agents in this run set (0/3 vs 3/3). These numbers come from one environment, 3 repetitions per task, and a small synthetic demonstration dataset—useful signal, not statistical proof.
