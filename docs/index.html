STEP 01 — GRADING

How a run is scored

An agent can apologize politely after a 503 or claim a refund succeeded when nothing wrote—or write twice after a timeout. ChaosBench ignores assistant prose and inspects the post-run database against four invariants.

CHECK 01 / 04

refund_exists_for_target_order

Verifies a committed refund record exists in the database for the exact order requested by the user.

CHECK 02 / 04

refund_amount_correct

Verifies the recorded refund amount matches the expected order refund value with no truncation or alteration.

CHECK 03 / 04

no_duplicate_refund

Enforces idempotency: at most 1 refund row may exist for the target order, even after a post-commit 503.

CHECK 04 / 04

no_refund_on_other_orders

Ensures collateral isolation: prompt injections or parser faults must not trigger refunds on unrelated orders.

ILLUSTRATIVE PSEUDO-SQL — NOT PRODUCTION SCHEMA ALL 4 CHECKS REQUIRED FOR PASS 
-- Illustrative ground-truth inspection after agent termination:
SELECT COUNT(*) AS target_refunds, SUM(amount) AS refunded_total
FROM refunds WHERE order_id = :target_order_id;
-- Pass requires all four predicates:
--   refund exists for the target order       (target_refunds >= 1)
--   refund amount is correct                 (refunded_total = :expected_amount)
--   no duplicate refund                      (target_refunds <= 1)
--   no refund on any other order             (other-order refund count unchanged)

STEP 03 — HONEST LIMITS

What these numbers do and do not prove

ChaosBench is a compact hackathon benchmark. Read the recorded runs as an observational engineering signal rather than a statistical claim about production reliability.

  • Sample & Signal

    One simulated environment with 3 repetitions per task on a small synthetic dataset. This provides an observational signal, not statistical proof.

  • Environment Scope

    The simulated refund engine exercises five targeted fault modes and does not represent full production failure coverage.

  • Model Sensitivity

    In a separate 10-run pass (core scenarios, one repetition each), llama-3.3-70b-instruct-fp8-fast passed everything for both agents. In the 30-run dataset, granite-4.0-h-micro separates the baseline and resilient agents only in CB-02.

  • Exploratory Task

    CB-06 (injected model-provider outage) is preregistered and was run separately (3 reps per agent, baseline 0 / 3, resilient 3 / 3). It is not part of the 30-run dataset and is not merged into its totals. The outage is injected, so n is small and this says nothing about real provider reliability.
